## 1. 设计原则

### 1.1 为什么这样建模

1. **服务于四段旅程，不服务于范式。** 建立顺序是 家庭 → 站点 → 计划 → 决策 → 归因 → 异常。每一天的计划都是独立记录（`EnergyPlan`），因为它要被接受、调整、锁单、覆盖，是"当天可操作的一件事"，不是持续状态。
2. **每一层解释都有宿主实体。** L1 在 `DecisionLog.actionSummary`，L2 在 `explainL2`，L3 在 `explainL3`。**不允许把某层解释塞进页面临时变量**——三层都必须能被单独查询与导出。
3. **弃权与执行平级。** `ForgoneOpportunity` 是与 `PlanSlot` 平级的实体，不是附属字段。任何一天"弃权项为空"即判数据不合格（总 PRD §6.4）。
4. **不确定性是一等公民。** `Interval`（区间）、`confidence`（置信度）、`uncertaintyDeclared`（声明不知道）覆盖所有预测性输出。凡预测，必带区间。
5. **状态机是家庭级单例。** `RunModeState` 挂在家庭上被所有页面读取，降级状态的传播不依赖页面。
6. **模型层不格式化。** 金额一律为欧元浮点数，格式化属于视图层。

### 1.2 类型命名规范

| 规则 | 说明 | 正例 | 反例 |
|---|---|---|---|
| 实体接口用名词单数、大驼峰 | 与类型文件一致 | `BatteryHealth` | `BatteryHealthData` |
| 嵌套结构用"主体 + 修饰" | 归属清晰 | `BatteryHealthPoint` | `Point` |
| 联合类型用**小驼峰短横线**字面量 | 禁止大写与下划线 | `'grid-charge'` | `'GridCharge'` |
| 级别枚举统一 `L` + 数字字符串 | 便于排序 | `'L1' \| 'L2'` | `1 \| 2` |
| 展示文案字段以 `Label` 结尾 | 视图直接渲染，不二次拼接 | `actionLabel` | `actionText` |
| 人话解释字段以 `reason` / `note` / `summary` 结尾 | 一律写成完整句子 | `reasonSkipped` | `reasonCode` |
| 金额以 `Eur` 结尾、时长带单位后缀 | 单位自解释 | `earningEur`、`durationMin` | `amount`、`backupTime` |

### 1.3 只读约束

类型文件中**每个字段都是 `readonly`**。这是产品立场的代码化，不是风格偏好：

1. **界面交互不得原地修改实体。** 点"接受计划"是把 `EnergyPlan.locked` 的新对象写回数据源，旧对象必须保留。
2. **更正与撤回必须留痕**（总 PRD §7.4 第 6 条）。被推翻的决策不删不覆盖：新决策写入新 `DecisionLog`，旧记录的 `overridden` 被填上，同时写入一条 `AuditEntry`。
3. **原型期状态保存在内存**（总 PRD §11.3）。模拟数据模块导出的是一棵**不可变的初始状态树**，交互通过结构化克隆产生新对象，禁止 `push` 与直接赋值。
4. **可选性规则**：类型文件中**没有任何 `?` 可选字段**。"可以没有"统一用 `T | null` 显式表达，使校验清单能逐字段穷举，不必区分"字段缺失"与"字段为空"。

### 1.4 时间口径

| 项 | 约定 |
|---|---|
| 时区 | `Europe/Berlin`，夏令时 UTC+02:00 |
| 完整时间戳 | ISO 8601 带偏移，如 `2026-06-17T18:42:00+02:00`。禁止裸时间戳 |
| 日期 / 时刻 | 日期 `YYYY-MM-DD` 按本地日切分；时刻 `HH:mm` 24 小时制零填充 |
| 月份标签 | `YYYY-MM` |
| 夏令时切换 | 3 月与 10 月最后一个周日。切换日仍按 24 小时刻度展示，`socCurve` 用 `00:00`–`23:45` 固定 96 点不断点 |
| 新鲜度判断 | 以运行时本地时间为准，不使用模拟数据的固定"现在" |

### 1.5 货币口径

1. **原型期只用欧元**（总 PRD §7.4 第 1 条）。展示统一 `€0.00`，负号前置（`−€0.42`），不用括号表示负数。
2. 金额字段名以 `Eur` 结尾；比例字段用 0–1 小数（`solarConfidence: 0.88`）或百分数（`sohPercent: 97.4`），两者不混用，字段名必须自证。
3. **毛利与净利分开**：`grossEur` 与 `netEur` 同时存在；界面默认只出现 `netEur`，`grossEur` 仅作计算过程（总 PRD §7.4 第 4 条）。
4. 写入模型前四舍五入到两位小数；校验允许 ±0.005 累计误差。
5. **门槛金额不对用户裸露**，以档位文案呈现（"为几毛钱不值得伤电池"），欧元值只在深水区出现。

### 1.6 界面可见性的三级定义

| 标记 | 含义 | 规则 |
|---|---|---|
| **主** | 默认出现在界面上 | 必须成人话；不得出现 SOC / DoD / EFC / kW / kWh 裸术语 |
| **深** | 默认折叠，用户主动展开后出现 | 可为专业数值，但必须带单位与来源 |
| **内** | 不进界面 | 仅驱动逻辑、校验、导出与安装商后台 |

### 5.1 备电可用时长（主展示值）

**定义**：把剩余电量按"只保基础设备"的负荷折算成小时数。这是备电**唯一对用户可见的数字**（总 PRD §4.9：备电预留比例这个词永远不出现在用户界面）。

常量（本户）：额定容量 `C = 10.2 kWh`；硬件最低电量比例 `f = 0.05`；放电效率 `η_dis = 0.95`；备电基础负荷 `P_ess = 0.62 kW`（冰箱 + 照明 + 网络 + 安防 + 锅炉水泵与控制器 + 必要待机）。**取偏保守的负荷口径，宁可少报不多报。**

```
usableKwh        = (soc / 100 × C − f × C) × η_dis
backupHoursLeft  = usableKwh / P_ess
```

展示规则：四舍五入到最近的 **0.5 小时**；不足 1 小时显示"不足 1 小时"；超过 24 小时显示"一天以上"。文案统一为"够你家基础用电约 X 小时"，不出现百分比。校验用：`|backupHoursLeft − 按上式重算的值| ≤ 0.25`。

| soc | usableKwh | 精确时长 | 展示 |
|---|---|---|---|
| 100% | 9.20 | 14.84 | 15.0 小时 |
| 62% | 5.47 | 8.83 | 9.0 小时 |
| 48% | 4.17 | 6.72 | 6.5 小时 |
| 35% | 2.91 | 4.69 | 4.5 小时 |
| 20% | 1.45 | 2.34 | 2.5 小时 |

**反算备电预留底线**：用户在冷启动只回答小时数 `H`，Agent 反算预留 SOC：

```
预留 SOC = roundUp5( (H × P_ess / η_dis + f × C) / C × 100 )
```

`roundUp5` 表示向上取整到 5% 的整数倍。取 `H = 4`：`(4 × 0.62 / 0.95 + 0.51) / 10.2 × 100 = 30.6%` → 向上取整到 **35%**。这个值就是本户的备电预留底线，**任何套利动作都不得让 SOC 低于它**。

### 5.2 等效满循环（EFC）的折算

**定义**：把每一次充放动作按其深度折算成"放满一次电池"的份额。

```
单次动作 ΔEFC = 本次放出电池的直流电量 DC_discharge(kWh) / C
ΔEFC = DC_discharge / C × k_temp
```

| `k_temp` | 条件 |
|---|---|
| 1.00 | 10 ≤ 电池温度 ≤ 35 摄氏度 |
| 1.10 | 0 ≤ 温度 < 10，或 35 < 温度 ≤ 45 |
| 1.25 | 温度 < 0 或 温度 > 45 |

**为什么按放电侧计**：质保条款通常以放电吞吐计循环；按充电侧计会因效率损失而低估消耗，与质保争议时的口径不一致。
**为什么不做深度修正**：EFC 的定义已按电量折算，再叠一层深度系数会造成双重惩罚，且无法与质保口径对齐。深度只用于触发单次深度告警（DoD > 80% 记 L1）。

当日合计 `plannedEfcUsed = Σ 各时段 ΔEFC`。

```
寿命消耗% = plannedEfcUsed / warrantyEfcLimit × 100 = plannedEfcUsed / 6000 × 100
展示：保留两位小数；不足 0.01% 时显示 "<0.01%"
每 EFC 折旧 = 电池组更换成本 / (warrantyEfcLimit × C) = 6500 / (6000 × 10.2) = €1.062
每 kWh 放电折旧 = €0.104 ≈ €0.105
```

算例：某日 `plannedEfcUsed = 0.42` → 寿命消耗 `0.42 / 6000 × 100 = 0.0070%` → 展示 `0.01%`。

### 5.3 净收益的 8 项构成

**总恒等式（唯一必须成立的一条）**

```
净收益 netEur = 基准购电支出 − 实际购电支出 + 上网收益 − 税费与上网结算费用影响 − 电池循环折旧
```

`基准购电支出` 的基线是"什么都不做"：没有光伏、没有电池，全部用电按当时的总电价从电网购买。

| # | 项目 | 方向 | 算式 | 口径说明 |
|---|---|---|---|---|
| 1 | 光伏自用节省 | + | `Σ_t 光伏直接供负载的 AC 电量 × 该时刻零售电价` | 只算不经电池的部分，避免与第 3 项重复 |
| 2 | 低价充电节省 | + | `Σ_t 电网充入电池的 AC 电量 × (当日被顶掉的加权零售电价 − 该时刻零售电价)` | 当日未从电网充电时为 0 |
| 3 | 高价放电节省 | + | `Σ_t 电池放出供负载的 AC 电量 × 该时刻零售电价 − 光伏充入电池的 AC 电量 × 上网电价` | 减项是"这些光伏如果不存进电池能卖掉"的机会成本 |
| 4 | 上网收益 | + | `上网 AC 电量 × 上网结算电价（本户 €0.078/kWh）` | 总 PRD 未单列，本文新增（偏差 C1） |
| 5 | 电网费规避 | + | `Σ_t (光伏直接供负载 + 电池供负载) 的 AC 电量 × 该时刻电网费单价` | 从第 1、3 项**剥离**出来单列，所以 1、3 只用零售电价 |
| 6 | 往返效率损失 | − | `(充入电池 AC 电量 − 放出电池 AC 电量) × 电池加权充电成本单价` | 光伏充入部分按上网电价（机会成本口径），电网充入部分按实际充入价 |
| 7 | 电池循环折旧 | − | `当日 ΔEFC × 每 EFC 折旧额` | 见 §5.2 |
| 8 | 税费与上网结算费用影响 | − | **平衡项**：`(第 1–7 项之和) − 净收益` | 见下方残差规则 |

**残差规则**：第 1–7 项的切分不可避免地带有口径残差。本规范规定**残差一律计入第 8 项**，并要求 `|feeAndTax| ≤ 0.02 × 基准购电支出`；超出该界限说明前 7 项算错了，数据判为不合格。

**参考夹具（2026-06-17，Karlsruhe，晴天）**：基准购电支出 €4.71，实际购电支出 €0.15，上网 23.10 kWh（€1.80），当日 ΔEFC 0.42，净收益 €5.59。

| # | 项目 | 金额 |  | # | 项目 | 金额 |
|---|---|---|---|---|---|---|
| 1 | 光伏自用节省 | +€2.04 |  | 5 | 电网费规避 | +€0.94 |
| 2 | 低价充电节省 | +€0.00 |  | 6 | 往返效率损失 | −€0.42 |
| 3 | 高价放电节省 | +€1.88 |  | 7 | 电池循环折旧 | −€0.63 |
| 4 | 上网收益 | +€1.80 |  | 8 | 税费与上网结算费用 | −€0.02 |
| — | — | — |  | — | **合计** | **€5.59** |

（`0.02 ≤ 0.02 × 4.71 = 0.094`，残差在界内。）

### 5.4 三个差额

三个差额回答三个不同问题，**口径与符号方向必须固定在文档与代码里**，不得各页面各写一套。

| 代号 | 名称 | 含义 |
|---|---|---|
| `B` | 什么都不做 | 没有光伏也没有电池，全部用电按当刻总电价购买 |
| `F` | 出厂默认策略 | 光伏 + 电池按"自发自用优先"运行，效率与折旧同口径 |
| `A` | 管家 Agent 调度 | 实际执行（影子期为"如果按我说的做"） |
| `T` | 理论最优 | 事后用真实电价与真实发电量做的离线最优调度，不违反硬约束 |

| 差额 | 算式 | 正号含义 | 对应话术 |
|---|---|---|---|
| 与出厂策略的差额 | `Δ1 = F − A` | 管家比出厂策略省得多 | "比出厂策略再省 €13.20" |
| 与"什么都不做"的差额 | `Δ2 = B − A` | 整套系统的总价值 | "这个月一共省了 €76.86" |
| 与理论最优的差额 | `Δ3 = A − T` | 还有多少没拿到的空间 | "还有 €6.90 的空间，我没拿满" |

**闭合约束**：`Δ2 = (B − F) + Δ1`；`B − T = Δ1 + Δ2 + Δ3`；`netEur = Δ2`。

**参考夹具（2026 年 5 月，本户）**

| 栏 | 账单 | 差额 | 差额话术 |
|---|---|---|---|
| 什么都不做 | €185.06 | — | 基准 |
| 出厂默认策略 | €121.40 | +€63.66 | 硬件本身的价值 |
| **管家 Agent 调度** | **€108.20** | **+€13.20** | **本产品创造的价值** |
| 理论最优（事后回看） | €101.30 | +€6.90 | 诚实披露上限 |

逐项校验：`Δ1 = 13.20`、`Δ2 = 76.86`、`Δ3 = 6.90`；`Δ2 = (B − F) + Δ1 = 63.66 + 13.20 = 76.86`，闭合。

### 5.5 光伏预报置信度

取值范围 `solarConfidence ∈ [0.40, 0.98]`。低于 0.40 时不做预报，直接进入不确定声明。来源为气象服务商给出的不确定性区间，按"预报光照强度的相对标准差"折算。

| 区间 | 档位 | 展示文案 | 对计划的约束 |
|---|---|---|---|
| 0.85–0.98 | 高 | "预计今天屋顶能发 36 度电" | 正常优化 |
| 0.70–0.85 | 中 | "预计今天屋顶能发 30–36 度电" | 正常优化，区间按 ±12% 给出 |
| 0.55–0.70 | 低 | "这个时段的判断不太可靠，我采用了更保守的做法" | **不得依赖套利窗口**；向自发自用收敛；必须至少产出 1 条 `reasonKind = 'uncertainty'` 的弃权项 |
| 0.40–0.55 | 很低 | "今天我不敢猜，先按最保守的方式安排" | 降级为保守模式，`RunModeState.reason` 必填；计划只保留 `solar-priority` 与 `idle` |

数值约束：`solarForecastKwh` 必须落在按装机容量与季节推算的合理区间内（本户 8.4 kWp：夏 20–45、春/秋 8–30、冬 1–12），超上限即判数据不合格。

### 7.5 随机但不失真的生成规则

1. **固定种子。** 所有随机量使用带固定种子的伪随机数发生器（种子写在模拟数据模块顶部常量里）。刷新页面必须得到同一组数据，评审截图才能复现。
2. **形状来自模板，幅度来自噪声。**
   - 电价曲线：以"早峰（07:00–09:00）+ 午间低谷（11:00–14:00）+ 晚峰（17:00–21:00）"为形状模板，每小时叠加不超过 ±8% 的噪声；午间低谷必须允许穿越零点成为负值，**至少每 7 天出现 1 次负电价**。
   - 负荷曲线：年度趋势（夏低冬高）× 周内趋势（周末高）× 日内形状 × 噪声，噪声幅度不超过基础值的 12%。
   - 光伏曲线：晴空模型（正弦半波，日出约 05:15、日落约 21:30）× 当日云量系数（0.35–1.00），再叠加不超过 ±5% 的瞬时噪声。
3. **不产生物理上不可能的瞬间。**
   - 电池功率不超过 `inverterKw − 家庭当前负荷`（放电）或 `inverterKw`（充电）。
   - SOC 变化必须与功率、时长、容量一致：`ΔSOC = powerKw × Δh / C × 100 × 效率`。
   - 光伏瞬时功率不超过 `pvKwp × 0.95`。
4. **异常值是"设计出来的"，不是"随机出来的"。** 所有 L1/L2/L3 事件都由 S 系列故事线显式指定，随机过程不得产生额外事件，否则页面状态无法穷举。
5. **小数位纪律。** 功率一位、SOC 一位、金额两位、EFC 两位、置信度两位。禁止在数据里出现 5 位以上的浮点数。
6. **文案纪律。** 所有 `reason` / `note` / `summary` / `suggestion` 类字段由人工撰写，不得由数值拼接生成——拼接出来的文案不会有因果关系，会直接违反"弃权必须解释"的要求。
7. **占位禁则。** 不得出现 `TODO`、`示例`、`XXX`、`lorem` 等占位内容；不得出现任何 emoji。

### 7.6 数据自洽性约束

| # | 约束 | 说明 |
|---|---|---|
| C1 | **计划表首尾相连** | `slots[i].socTo === slots[i+1].socFrom`（±0.1），且相邻时段 `end === next.start` |
| C2 | **计划与电量曲线对齐** | `slots[0].socFrom` 等于 `socCurve` 首点、`slots[last].socTo` 等于末点；每个 slot 边界在 `socCurve` 上的插值一致（±0.5） |
| C3 | **能量守恒** | `Σ 充电 DC − Σ 放电 DC = (末 SOC − 初 SOC)/100 × C`（±0.05 kWh） |
| C4 | **收益拆解闭合** | 8 项之和 = `netEur`（±0.005）；5 个正项之和 = `grossEur`（±0.005）；`grossEur ≥ netEur` |
| C5 | **四栏差额闭合** | `compare[0].billEur − compare[2].billEur = netEur`；`compare[i].deltaEur = compare[i−1].billEur − compare[i].billEur`；`compare[0].deltaEur === null` |
| C6 | **事件与模式一致** | 存在未闭环的 L3 事件时 `RunModeState.mode` 必须是 `safe` 或 `manual-hold`；存在未闭环的 L2 待确认时模式必须是 `conservative` 或更严 |
| C7 | **折旧与预算一致** | 某周期内 `Σ 每日 ΔEFC` 等于该周期 `CycleBudget.usedEfc`（±0.1）；年度 `Σ 各月 usedEfc` 等于年账 `usedEfc`（±0.2） |

**特别提醒**：C3 与 C7 是这套模拟数据最容易出错的两条。建议在生成器里先跑一遍"能量账"，把 C3 的残差摊回到 `idle` 时段的 `powerKw` 上，再跑一遍"循环账"。
