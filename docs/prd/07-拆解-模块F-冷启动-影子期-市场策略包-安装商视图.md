5. **策略包与熔断都不得触碰硬件安全参数**（电压、保护阈值、并网参数）：这类参数在管家内不存在写入路径。
6. **影响多户的规则变更必须人工批准 + 灰度 + 回滚预案**；影响 > 50 户强制经护栏复核人批准（§5.4、§10.3）。

# 第一章 T1 冷启动三问 · 字段级规格

## 1.1 目标与完成标准

目标：在不要求用户理解任何技术参数的前提下拿到三件事——偏好配比、备电保障目标、自动化意愿，并翻译成 Agent 可执行的初始边界。完成标准：10 分钟内完成；**单屏完成，无"下一步/上一步"**；三问都可用默认值直接通过。落库 `OnboardingAnswers`（附录 A），派生写入 `PreferenceWeights`、`Guardrail`、`RunModeState(mode='shadow')`。

## 1.2 单屏布局与响应式

按 §3.2 的 12 列硬网格排布。

| 栏位 | 网格占位（1440 基准） | 内容 |
|---|---|---|
| 标题行 | 全宽 96px | 「先定三件事，我就能开始」+ 右上角 `[以后再说]` |
| 问 1 块 | 左 4 列标签 / 右 8 列控件 | 「你更在意什么？」+ 配比滑杆组 |
| 问 2 块 | 左 4 列标签 / 右 8 列控件 | 「停电时，你最需要保证什么？」+ 时长三选 + 追加设备多选 |
| 问 3 块 | 左 4 列标签 / 右 8 列控件 | 「你希望我多主动？」+ 三选一 |
| 底部操作条 | 全宽固定 72px | 左 `[用默认值开始]`；右 `[开始学习]`（主按钮） |

| 断点 | 处理 |
|---|---|

## 1.3 问 1 · 你更在意什么？（配比滑杆）

三个诉求互相冲突（§2.4），故必须是**配比**而非单选；做成单选会让用户误以为另外两项不管了。

| 项 | 规格 |
|---|---|
| 类型 | 三条联动滑杆：「把电费省下来」「停电时不慌」「电池用得久一点」 |
| 取值范围 / 步长 | 每项 10–60，步长 5；三项之和恒等于 100；单项不得低于 10 |
| 界面初始位置 | 40 / 40 / 20（遵循 §4.9） |
| 联动重分配 | 拖动项变化 Δ，从其余两项按当前值比例分摊 −Δ，各按 5% 取整，余数补给较大项 |
| 触界处理 | 某项已到 10 或 60 时，其应分摊部分转由另一项承担；两项都触界则拒绝本次拖动并提示「三项都得留一点」 |
| 实时反馈 | 滑杆下方一行文案随配比变化（见下表） |

| 预设按钮 | 省钱 / 备电 / 护电池 | 用户可见说明 |
|---|---|---|
| 省钱优先 | 50 / 30 / 20 | 「我会更积极地抓电价低的时段」 |
| 停电优先 | 30 / 50 / 20 | 「我会先把停电要用的电留出来」 |
| 电池优先 | 30 / 30 / 40 | 「我会少让电池做事，收益会低一些」 |
| 均衡（默认） | 40 / 40 / 20 | 「三样都照顾，偏保守」 |

映射结果写入 `PreferenceWeights`：`earn` / `backup` / `battery`（各 10–60，步长 5，`sum` 恒 100）、`source`（`onboarding` / `onboarding-deferred` / `settings` / `quarterly-review` / `marketpack-default`）、`version`（每次变更 +1，不允许原地覆盖）、`updatedAt`、`updatedBy`。

## 1.4 配比 → 派生参数的映射表

判定按优先级自上而下，命中即返回；判定基于单项权重，不基于排序。

| 优先级 | 条件 | 收益门槛档位 | 循环预算系数 | 灾害季备电上浮 | 用户可见档位文案 |
|---|---|---|---|---|---|
| 1 | `battery ≥ 40` | 严格（×1.30） | ×0.75 | 不改 | 护电池强度 = 保守 |
| 2 | `battery` 20–35 | 标准（×1.00） | ×1.00 | 不改 | 护电池强度 = 平衡 |
| 3 | `battery ≤ 15` | 宽松（×0.85） | ×1.15 | 不改 | 护电池强度 = 宽松 |
| 4 | `earn ≥ 50` | 覆盖为宽松（×0.85） | 不变 | 不改 | 「我会更积极一点」 |
| 5 | `earn ≤ 25` | 覆盖为严格（×1.30） | 不变 | 不改 | 「便宜得不明显我就不动手」 |
| 6 | `backup ≥ 50` | 不变 | 不变 | 开启，×1.15–1.30 | 「停电优先」 |
| 7 | `backup` 40–45 | 不变 | 不变 | 仅极端天气预警 ×1.15 | 默认 |
| 8 | `backup ≤ 35` | 不变 | 不变 | 关闭 | 「只在日常范围内留电」 |

冲突处理：`battery` 与 `earn` 规则同时命中时（例：省钱 10 / 备电 50 / 护电池 40），**以更保守的一方为准**（门槛取严格、预算取小系数），依据 §2.5「默认值必须保守」。门槛只以**档位**出现在界面，不暴露金额（§6.1）。每次权重变更必须给一句影响说明，例：「这次你更看重电池寿命，我会少做几次套利，预计收益会低一些」。

## 1.5 问 2 · 停电时，你最需要保证什么？

备电是本产品最不能犯错的一项（§2.6 护栏指标「备电失守次数 = 0」）。本问把用户的**生活语言**转成内部预留值，用户全程不接触百分比。

| 基础设备包选项（冰箱 + 照明 + 网络） | 默认 | 用户可见文案 |
|---|---|---|
| 4 小时 | 否 | 「够撑到电力恢复，或者撑到天亮」 |
| **8 小时** | **是** | 「一般停电都能覆盖」 |
| 12 小时 | 否 | 「长时间停电也不慌」 |

| 基础设备包功率（内部示例值） | 功率 |
|---|---|
| 冰箱（含压缩机启动余量，按日均功率折算非峰值） | 0.12 kW |
| 照明（3–5 个房间，LED） | 0.10 kW |
| 网络（光猫 + 路由 + 逆变器通信；断网会导致远程支持不可用，计入必需） | 0.13 kW |
| 合计 `baselineBackupLoadKw`（计算基准） | 0.35 kW |

| 追加设备（多选，默认全不勾） | `extraLoadKw` | 勾选后的额外影响 |
|---|---|---|
| 医疗设备（呼吸机等） | +0.15 kW | 最高保护档：备电不可被任何套利侵占；停电按 L3 通知；季度复核必列 |
| 居家办公（网络 + 电脑 + 显示器） | +0.20 kW | 工作日白天备电不被占用 |
| 鱼缸 / 爬宠加热 | +0.10 kW | 冬季默认建议勾选 |
| 电动门 / 安防 / 电围栏 | +0.05 kW | 南非策略包默认勾选 |
| 没有别的 | 0 | 与其余选项互斥 |

映射结果：界面选择 → `backupHoursRequested`（4 / 8 / 12）；设备勾选 → `extraLoadKw`（求和）；两者送入第二章公式，得内部 `backupReserveSocPct` 与界面唯一展示值 `backupReserveHours`；结果同时写入 `Guardrail`（分组「你可调整」、`level = L3`）。

## 1.6 问 3 · 你希望我多主动？

| 选项 | 默认 | 存储值 | 对模式的含义 |
|---|---|---|---|
| 只给我建议，我自己决定要不要按 | 否 | `advisory-only` | 影子期后落点为 Advisory，自动化默认关闭 |
| 帮我自动执行，但每次都告诉我 | **是** | `auto-notify` | 影子期后可选落入 Auto，每条动作推送告知 |
| 帮我自动执行，有异常再找我 | 否 | `auto-exception` | 影子期后可选落入 Auto，仅异常与日报告知 |

关键澄清：无论选哪项，**初次开通一律先进入影子期**，本问只决定影子期结束后的默认落点与告知密度，**不构成自动执行授权**（§3.4 旅程 A）。因此本问不写 `Auto` 状态、不写 `PendingApproval`。第 1 项同时满足 §2.5 的要求——保守型用户需要的「只建议，不执行」开关必须在首次引导里看得见。

# 第二章 备电预留的换算说明（产品与实现视角）

> 本章为内部文档，**其中任何数字与百分比都不得进入用户界面**。作用是让产品与研发对"用户选 8 小时 → 系统留多少电"有同一套算法与同一批输入。

## 2.1 硬规则

1. 备电预留比例**永不进入用户界面**，含深水区展开、影子期对照表、安装商详情、对客导出件。
2. 界面与备电有关的数字只有一种形式：**「停电时够用 X 小时」**。
3. 备电预留是硬约束，任何套利动作不得侵占（§6.4 第 2 条、§9.1）。
4. 换算一律取**保守侧**（向上取整），宁可多留一点。

## 2.2 换算所需的输入项

| 输入项 | 来源 | 示例值 | 用户可见 |
|---|---|---|---|
| `baselineBackupLoadKw` | T1 基础设备包功率表 | 0.35 kW | 否 |
| `extraLoadKw` | T1 追加设备 | 0.15 kW | 以设备名称形式可见 |
| `backupHoursRequested` | T1 时长选择 | 8 小时 | 是 |
| `usableCapacityKwh` | `Site` / `BatteryState` | 10 kWh | 否 |
| `dischargeEfficiencyPct` | 电池与逆变器参数 | 92% | 否 |
| `reserveFloorPct` / `reserveCapPct` | 系统强制（设备与化学安全下限 / 给调度留空间） | 10% / 90% | 否，不可调 |
| `seasonalUpliftFactor` | 策略包 + 天气预警 | 1.00（灾害季 1.15–1.30） | 只以文字表述 |

## 2.3 换算公式

```
loadKw      = baselineBackupLoadKw + extraLoadKw
requiredKwh = loadKw × backupHoursRequested          # 负载侧需要的电量
storedKwh   = requiredKwh ÷ dischargeEfficiencyPct   # 折算到电池侧
rawPct      = storedKwh ÷ usableCapacityKwh × 100
reservePct  = ceil(rawPct × seasonalUpliftFactor)    # 向上取整，取保守侧
reservePct  = clamp(reservePct, reserveFloorPct, reserveCapPct)
```

实现要求：向上取整到 1%，不得四舍五入到用户不利的一侧；季节、天气、容量变化触发重算（§2.6）；该值不写入任何面向用户的接口响应，前端若需展示必须经"人话转换"后只返回小时数。

## 2.4 示例算例（数字为示例假设）

- **算例 A · 基础包 8 小时（默认路径）**：`0.35 × 8 = 2.80` → `÷0.92 = 3.04 kWh` → `÷10 = 30.4%` → 31%，上浮系数 1.00。界面只显示「停电时够用 8 小时」。
- **算例 B · 加入医疗设备**：`(0.35+0.15) × 8 ÷ 0.92 = 4.35 kWh` → 43.5% → 44%。界面只显示「停电时够用 8 小时（含呼吸机）」；该家庭为最高保护档，任何套利不得侵占，停电按 L3 通知。
- **算例 C · 灾害季上浮**：算例 A 的 31% × 1.20 = 37.2% → 38%。界面只显示「这周有强天气预警，我把停电时要用的电多留了一些」。
- **算例 D · 达不到所选时长**：容量 5 kWh、负载 0.55 kW（含居家办公）、请求 12 小时 → `0.55 × 12 ÷ 0.92 = 7.17 kWh` → 143% > 上限 90%，夹紧到 90% 并触发"达不到"分支。

## 2.5 达不到所选时长时的反算与处理

```
achievableHours = floor( usableCapacityKwh × (reserveCapPct − reserveFloorPct) ÷ 100
                         × dischargeEfficiencyPct ÷ loadKw × 2 ) ÷ 2
```

算例 D 反算：`5 × 0.80 × 0.92 ÷ 0.55 = 6.69` → 向下半小时取整 → 6.5 小时。

界面文案三步：① 「以你这套电池和你选的设备，停电时最多能保证约 6.5 小时。」② 「做不到 12 小时，不是设置问题，是电池容量和设备用电量决定的。」③ 三个出口：`[改成 8 小时]` / `[保持 12 小时的目标，能撑多久算多久]` / `[减少必须保的设备]`。选「保持目标」时 `backupHoursRequested` 保留 12、`reservePct` 夹紧到上限，并在季度复核的备电体检中列为长期差距项。

## 2.6 重算触发与告知规则

触发重算的情形与告知方式：用户修改时长或设备清单 → L3 流程 + 影响说明；季节切换（策略包定义）→ 日报内一行（L1），不推送；极端天气 / 灾害预警 → 推送一次，说明「多留了一些」；电池可用容量变化（衰减、限功率）→ 仅当预留提高 > 5 个百分点时在日报内提一行；家庭用电画像显著变化 → 日报内一行。

不允许发生的事：未告知就下调用户的备电保障时长；数据缺失时用最后已知值继续驱动调度（§9.3）。

# 第三章 T2 影子期规格

> 影子期是"把黑盒变白盒"的唯一零风险窗口（§2.7 第 1 步）。它的目标不是产生收益，而是让用户**敢于**授权自动执行。

## 3.1 进度呈现与结束日期

看板顶部自上而下：① 当前模式条（全局组件，灰色条 +「我在学习，只看不做」）；② 线性进度条 `已过天数 / 总天数`（默认 14 天，可配 14–28 天）；③ 结束日期；④ 一行说明「这期间我只给建议，不会动你的电池」。

| 结束日期规则 | 说明 |
|---|---|
| 首选表达 | **绝对日期 + 星期**：「影子期到 2026 年 3 月 18 日（周三）结束」 |
| 次选表达 | 相对天数只作补充，不单独使用（「还有 7 天」） |
| 禁止 | 倒计时红色数字、闪烁、「只剩」这类制造紧迫感的词 |
| 结束后会发生什么 | 同一行说明：「那天我会给你一份小结，再由你决定要不要让我自动安排」 |
| 提前结束 | 任意时刻允许，按钮常驻，不设天数门槛 |
| 延长 | `[再观察一段时间]` 每次 +7 天，可多次，无次数上限 |

## 3.2 逐日「建议 vs 实际」对照表字段（`ShadowDay`）

| 字段 | 类型 | 业务含义 | 界面呈现 |
|---|---|---|---|
| `date` | string | 日期 | 「3 月 5 日 周三」 |
| `suggestedWindow` | `{start,end}` | 我建议的时段 | 「02:00–04:00」 |
| `suggestedAction` | string | 我建议做什么 | 「趁电价最低的时候充电」（人话） |
| `actualAction` | string | 实际发生了什么 | 「没有动作」/「18:00 充了电」 |
| `deviationKind` | `match \| partial \| opposite \| no-suggestion` | 一致 / 部分一致 / 方向相反 / 当天没建议 | 文字标签 + 图形编码（不靠颜色单独表达） |
| `earningDeltaEur` | number | 差多少钱（事后单点值） | 「如果按我说的做，这天大约少花 €0.61」 |
| `deltaBasis` | string | 差额口径说明 | 折叠，注明是否计入效率损失与折旧 |
| `dataComplete` | boolean | 数据是否完整 | 不完整时标注「这天数据不全，仅供参考」，且不计入小结合计 |
| `note` | string \| null | 一行补充 | 「那天你出门了，家里用电少」 |

表格规则：至少展示最近 7 天，更多可展开；当天对照未就绪时显示「今天的对照明天早上出来」；差额一律用「大约」「如果按我说的做」，可点击打开解释模块（第八章）；不得出现备电预留比例或任何内部量，只出现小时与金额。

## 3.3 影子期小结的产出结构与文案

结束日推送一次，也可由用户随时主动生成。四段固定，顺序不可换。

| 段 | 内容 | 文案模板 |
|---|---|---|
| ① 一句话结论 | 区间表述，不给承诺 | 「这 14 天里，如果按我说的做，你家的电费**大概**会少 €8–12。」 |
| ② 数字对照 | 实际发生 / 如果按建议 / 差额 | 「实际 €26.4；按我说的做约 €18–20；差约 €6–8。」 |
| ③ 我从你家学到了什么 | 3–5 条 `kind='fact'` 的画像事实 | 「你家晚上 6–9 点用电最集中」「白天下班前基本没人」 |
| ④ 我建议的下一步 | 三个按钮 | `[现在就开始自动]` / `[再观察一段时间]` / `[有些地方我想先改改]` |

文案要求：不制造焦虑，禁止「你就这样浪费了两周」，改为「接下来我可以帮你把这些省下来」；数字必须带区间与「大概」，并声明口径（是否含效率损失与折旧）；数据不足时不硬算，改为「这 14 天里有 4 天数据不全，我先不给你算总账，免得算错」（宁少报不多报）；③ 中每条事实可一键否认（`[不对]`），否认后立即反馈「我会怎么变」。

## 3.4 「可主动跳过但不可自动跳过」的实现要求（六项，缺一不可）

1. **按钮常驻**：`[现在就开始自动]` 从第 1 天起即可见可点，不设「满 7 天才允许」之类的门槛。
2. **无计时器**：前端与后端都不存在能把 `shadow` 自动推进到 `advisory` / `auto` 的定时任务；影子期结束只产生**小结与提醒**，不产生状态迁移。
3. **接口层校验**：模式迁移接口必须要求 `actor = user` 与 `confirmed = true`；来源为 `system` 的 `shadow → advisory/auto` 请求一律拒绝并记审计日志。
4. **不做预授权**：结束页不得预先勾选「到期后自动开启」，不得把「开始自动」写进任何批量同意条款。
5. **可测**：模拟「完成三问后 60 天零操作」，`RunModeState.mode` 必须仍为 `shadow`（本文 §9.2 验收第 10 条）。
6. **延长不改变状态**：`[再观察一段时间]` 只延长天数，不迁移模式，不写 `PendingApproval`。

## 3.5 跳过时的二次确认文案

点击 `[现在就开始自动]` 进入**全屏确认页**（不用模态弹窗，避免误触，与 §4.1 交互习惯一致）。

- 标题：「现在就开始自动安排？」
- 正文三句：「影子期还剩 7 天没看完，跳过它我不会怪你。」「接下来我会真的控制电池什么时候充、什么时候放，规则用的是你定的那三条。」「每一次动作都能在决策日志里看到原因；随时可以点回『只给建议』。」
- 需勾选：「我了解，接下来管家会实际操作电池」（未勾选时主按钮不可点）。
- 主按钮 `[开始自动]`；次按钮 `[再观察一段时间]`。
- 底部固定一行：「不会改电压、保护阈值、并网参数这些安全设置，现在不会，以后也不会。」

禁止文案：「你就这样浪费了两周」「错过这段时间就白学了」「不建议跳过」。

## 3.6 影子期结束后的三个去向

三个去向与迁移结果：点击 `[开始自动]` 并完成确认页 → Shadow → Auto（确认页 + 留痕）；点击 `[先只给建议]` → Shadow → Advisory（自然结束或主动选择）；点击 `[再观察一段时间]` → 仍为 Shadow，天数 +7。三者都必须写 `AuditEntry`（谁、何时、从哪个模式到哪个模式、为什么）。

# 第四章 F8 市场策略包规格

> 解决 §1.5 业务目标 2：把「进入一个新市场」从固件排期变成运营配置。

| `fuseSwitch` | `{state,since,by,reason,affectedHouseholds,recoverPlan}` | 熔断开关状态（§4.5） |
| `rollbackSnapshotId` | string | 回滚快照引用 |

## 4.2 策略包详情页的区块顺序

顺序遵循「这是什么 → 会影响什么 → 会影响到谁 → 危险动作」，**不可调换**：

1. **头部**：市场名 + 版本号 + 状态标签 + 活跃用户数 + 健康状态。
2. **变更摘要**：与上一个 `live` 版本的差异，最多 5 条可展开；无变更时显示「本版本无实质变更」。
3. **电价机制**：机制类型 + 数据源列表 + 更新时间与可信度。
4. **电网费机制**：分时 / 容量费 / 需量费 / 可控负荷减免档位**及其代价**（`requiresCurtailment` 必须明写「换取减免需要接受电网限功率」）。
5. **上网规则**：是否允许 + 费率 + 是否划算 + 限制条件。
6. **需求响应机会**：有无 + 本期是否启用（恒为「只预埋」）。
7. **补贴与合规约束**：逐条标注来源与生效日期。
8. **当地默认红线**：与全局默认的差异高亮，并给一句人话理由（例：「南非电网不稳定，停电是常态，所以默认留 12 小时」）。
9. **规则变更提醒**（§4.3）：本市场未闭环的变更条目。
10. **全局熔断开关**（§4.5）：页脚独立区域，用边框与间距隔离，避免误触。

## 4.3 规则变更提醒列表字段

| 字段 | 说明 |
|---|---|
| `变更条目` | 一句话描述（例：「某零售商峰段调整，17:00–19:00 移入高价段」） |
| `类型` | 电价 / 电网费 / 上网规则 / 补贴合规 / 需求响应 |
| `生效日期` | 规则的实际生效日 |
| `影响存量用户数` | 按 `TariffProduct` 与市场匹配计算 |
| `影响方向` | 收益下 / 风险升 / 无实质影响（可多标） |
| `是否需要复核` | 由 `requiresRecheck` 决定 |
| `处理状态` | 待评估 / 已评估待批准 / 已批准待发布 / 已发布 / 已闭环 |
| `负责人` | 策略运营或护栏复核人 |
| `操作` | `[触发复核]` `[查看受影响用户]` `[标记为无影响]`（须填理由） |

「标记为无影响」必须填写理由并留痕，不允许静默关闭一条提醒。

## 4.4 触发存量用户复核的流程

1. **录入**：策略运营录入规则变更，生成变更条目（状态「待评估」）。
2. **算影响面**：计算受影响用户清单（匹配市场 + 电价产品 + 非 `retired` 状态）。
3. **审批门**：影响 > 50 户必须经护栏复核人批准，并附灰度方案与回滚预案，未附则无法进入下一步。
4. **分群**：收益受损 / 风险上升 / 无实质影响三类；**只对前两类发起复核**，第三类仅记日志、不打扰用户。
5. **通知**：对前两类各推一条（不重复）：「你所在的地区电价规则变了」+ 一句影响 + 一个入口。
6. **复核页**：变化是什么 → 对我意味着什么（收益区间 + 风险变化）→ `[保持现状]` / `[按新规则调整]` / `[我想先问一下]`；「按新规则调整」若涉及红线则走 L3 审批。
7. **留痕与回滚**：全过程写 `AuditEntry`；发布后 7 天内保留 `rollbackSnapshotId`，可一键回到上一版。

禁止：不得在用户不知情时改变其红线；不得把「规则变了」当营销理由推送收益预期。

## 4.5 全局熔断开关

**权限与位置**：位于策略包详情页页脚独立区域（视觉与其他开关隔离）；仅策略运营可**发起**、护栏复核人可**批准**，单人无法完成熔断（双人确认 + `AuditEntry`）；一次只能熔断一个市场，不支持批量熔断全部市场。

**二次确认文案（完整）**

- 标题：「熔断 {市场名} 的自动调度」
- 影响范围（三条必显）：① 「{市场名} 目前有 {N} 位用户处于自动或建议模式，熔断后他们全部进入**保守模式**：只做光伏优先与备电优先，不再执行任何套利动作。」② 「仍处于影子期的用户不受调度影响，但不会再收到新计划。」③ 「历史数据、收益记录、循环记账**全部保留**，熔断不删除任何记录。」
- 明确不做什么（两条）：① 「不会修改任何硬件安全参数（电压、保护阈值、并网参数）。」② 「熔断**不等于**回到出厂策略；回退出厂策略是用户自己的选择，与熔断无关。」
- 必填三项：熔断原因（≥ 20 字）；输入市场代码确认（如 `de-DE`，输错即失败，无跳过入口）；勾选「我已确认影响范围与受影响用户数」。
- 主按钮「提交熔断申请」（进入复核人审批后生效）；次按钮「取消」。

**受影响用户通知模板**

- **用户版（推送 + App 内消息，L2 级）**：标题「我把自动安排先停下来了」；发生了什么「我们发现在 {市场名} 有一个电价处理上的问题，为了稳妥，我先把自动安排停掉」；我做了什么「现在换成最保守的方式——优先用自家太阳能，先把停电要用的电留足，不再做买卖电价的动作」；对你有什么影响「停电时的用电不受影响；这段时间省的钱可能比之前少一点」；你需要做什么「什么都不用做。等我们确认没有问题，我会告诉你，并且问你要不要重新打开自动」。
- **安装商版（后台 + 邮件）**：「{市场名} 已熔断 —— 请留意客户来电。{N} 位客户已进入保守模式。原因：{内部根因摘要}。请勿向客户承诺恢复时间。统一客服话术见附件。预计恢复条件：{recoverPlan}。受影响客户清单见『安装商视图 → 筛选：熔断影响』。」
- **内部运营版**：含根因、影响户数、回滚快照 ID、灰度恢复计划、责任人、预计恢复时间。

通知纪律：熔断通知不受频率上限限制，但受静默时段约束——若在 23:00–07:00 提交，用户侧推送顺延至 07:00 后 30 分钟内，App 内消息即时可见（可见性不静默，只有推送通道静默，见 §7.2 第 6 条）。

**恢复流程**：根因闭环 + 复核人批准 → 先恢复 5% 用户（随机分组）观察 48 小时 → 观察期内不出现备电失守、循环预算超支、收益转负三类破线方可全量 → 全量时给用户一条说明并附本次修复的一句话 → **恢复不自动回 Auto**：受影响用户回到 Conservative，回到 Auto 需用户明确确认（与 §5.3「安全模式不自动回到自动模式」同一立场）。

两点解读：① 七个市场里没有一个「靠卖电赚钱」划算，本产品收益主线始终是**自用优化 + 电网费规避**，上网只是兜底；② 德国是唯一「两条曲线方向经常相反」的市场（电价低的小时不一定网费低），这正是 §1.9 选德国作为首选市场的技术原因。

## 5.2 为什么南非的默认备电显著更高

这不是保守偏好，而是**保险价值的量级差异**（§6.1：备电保险价值与停电风险正相关）。六条理由：

1. **停电不是异常，而是常态**。弱电网市场存在计划性减载，停电概率基数与其他市场不在同一量级。
2. **停电时长更长**。其他市场多为偶发数十分钟到数小时，当地单次可达 4–8 小时甚至更长；按「时长覆盖」设计的预留必须按更长续航折算。
3. **电网质量差带来额外余量**。电压与频率波动大，设备可能频繁脱离并网运行、以离网方式支撑家庭，实际消耗高于理论负载。
4. **关键设备构成不同**。除冰箱、照明、网络外，水泵、安防电围栏、电动门属必需负载，基础负载功率更高，因此当地策略包默认勾选「安防 / 电围栏」。
5. **用户分层要求**。§2.5 把「离网 / 弱网地区用户」单列，其核心诉求是「备电是刚需，套利次要」。
6. **产品形态已按简化版设计**。§10.1 明确南非做「备电优先 + 有限套利」；预留提高意味着可套利电量减少，因此收益预期在**产品层面**同步下调，而不是让用户自己发现收益变少。

配套要求：南非引导默认配比取 30 / 50 / 20；用户仍可下调备电时长，但**下调属 L3 变更**，确认页必须写明代价「少留电意味着停电时能撑的时间变短」。

## 5.3 默认值的覆盖优先级

优先级自高而下：**用户显式设置**（`PreferenceWeights` / `Guardrail`，永不被策略包覆盖）→ **市场策略包**（`defaultGuardrails` / `defaultPreferenceWeights`）→ **全局默认**（产品基线）。

策略包变更只能作用于**尚未显式设置过该项**的用户；已设置过的用户走 §4.4 复核流程，不能被静默改写。

## 6.3 远程支持工具（四个）

| 工具 | 入口 | 操作 | 产物 | 权限与留痕 |
|---|---|---|---|---|
| **与出厂策略对比** | 工具区第一项 | 选区间（7 / 30 / 90 天）→ 生成并排四栏对照 | 一句结论（「这段时间比出厂策略多省 €X」）+ 可导出 PDF（含口径与假设条件） | 只读；导出记 `AuditEntry` |

## 6.4 工单列表规格（`InstallerTicket`）

字段：工单号；来源（客户来电 / 系统告警 / 策略变更复核 / 沃太派单）；客户与关联异常（`Household`、`Incident.id`，后者可空）；级别与状态（L1–L3 / 新建、已接单、处理中、等客户、已闭环、已关闭）；负责人；SLA 到期时间；处置记录与最近更新（条目数 + 最近一条摘要 + 时间戳）。

**SLA 分级**：L3 = 15 分钟首响；L2 = 4 小时；一般咨询 = 2 个工作日；超时工单在列表顶部固定横幅提示。

**闭环回写（必填）**：关闭工单必须选择「这是一次性问题」或「这是系统性问题」；后者自动升级为规则变更任务（§4.7、§8.4）。

## 6.5 硬约束：安装商不能直接修改客户红线

**界面表达方式（五条）**

1. 红线区块内**不存在任何可编辑控件**：无滑杆、无输入框、无开关、无保存按钮。
2. 区块题注固定：「这些是客户自己定的边界。你可以发起变更建议，由客户确认；也可以引导客户在 App 的『电池 → 护栏』里自己改。」
3. 操作按钮文案是 `[发起变更建议]`，**不得**使用「修改」「调整」「设置」这类动词。
4. 只读值用纯文本 + 1px 边框表达；不可操作 ≠ 灰掉的禁用按钮（避免"看起来能点但点不动"）；L3 徽标 + 一行「由客户确认后生效」常驻。
5. 禁止任何绕道入口，包括「临时调整」「帮你先设上」「仅本次生效」「代客户确认」。

**技术校验（三条）**

1. 服务端权限矩阵对 `installer` 角色**拒绝** `Guardrail` 与 `PreferenceWeights` 的写接口调用，返回 403 并记审计日志；前端隐藏不是安全措施。
2. 「发起变更建议」只写入一条 `GuardrailChange(status='draft', origin='installer')`，生成客户侧待确认任务，审批人恒为**客户本人**（涉质保与安全参数的变更另需护栏复核人）。
3. 验收时必须有一条「安装商角色直接调用写接口」的测试用例，期望结果为拒绝（本文 §9.2 验收第 18 条）。

**允许安装商做的事**：查看、导出、发起变更建议、执行一键回退（需客户授权码）、生成话术、建工单、引导客户自行操作。

## 6.6 隐私边界（安装商侧）

客户姓名默认脱敏为「张先生」「M. Weber」，完整姓名仅在客户授权且工单进行中临时可见；不展示家庭成员数量、不在家时段推断、原始负荷曲线（可推断生活作息的敏感数据，§9.2）；家庭画像摘要只展示 fact 类且文案与客户在 App 中看到的一致；导出一律脱敏版本，确需原始数据走沃太售后正式流程并留痕。

# 第七章 设置页规格

> 设置页承担两件事：让用户能改边界（属 L3），以及让用户能**退出**（§9.4）。后者比前者重要。

## 7.1 偏好

| 字段 | 控件 | 取值范围 | 默认值 | 生效方式 |
|---|---|---|---|---|
| 省钱 / 备电 / 护电池 配比 | 三条联动滑杆（规则同 §1.3） | 每项 10–60，和恒 100 | 40 / 40 / 20 | **L3**：确认流程 +「这会改变什么」 |
| 停电时够用多久 | 三选一 + 自定义 | 4 / 8 / 12 / 自定义 2–24 整数小时 | 8（南非策略包 12） | **L3** |
| 电池寿命保护强度 | 三选一 | 宽松 / 平衡 / 保守 | 平衡 | **L3** |
| 为几毛钱不值得伤电池 | 三档滑杆（不显示数字） | 低 / 中 / 高 | 中 | **L3** |
| 给明天的太阳能留点空间 | 开关 | 开 / 关 | 关 | **L3** |
| 只给建议，我自己按 | 开关 | 开 / 关 | 关（保守型用户在首次引导可见） | **L2**（即时生效，需一次确认） |

**L3 变更的固定交互**：`[提交变更]` → 显示影响页（收益预估变化 + 风险变化 + 一句人话解释）→ 确认 → 状态为「待生效」或「已生效」（含审批人）→ 留痕。不允许即时生效，不允许原地覆盖历史值。界面上不得出现备电预留百分比、SOC、DoD、循环预算裸术语与具体门槛金额。

## 7.2 通知

| 字段 | 控件 | 取值范围 | 默认值 |
|---|---|---|---|
| 通道：App 推送 / 邮件 / App 内消息 | 开关 | 开 / 关 | 开 / 开（仅报告类）/ 开（不可关闭） |
| 通道：短信 / 电话 | 展示 | 固定关闭 | 关闭（§1.9：不默认使用） |
| 推送时间窗 | 时间范围 | 必须落在 07:00–23:00 之间 | 17:30–18:30 |
| 每日推送上限 | 数字 | 1–3 | 3 |
| 每周推送上限 | 数字 | 3–10 | 10 |
| 静默时段（自定义，可加一条） | 时间范围 | 见下方校验规则 | 无（系统强制区间始终生效） |

**通知类别（逐项开关）**：可关闭（L1）——次日计划、早晨简讯、日报周报、月度报告、寿命保护进度过半、季度复核提醒；不可关闭（L2）——备电被触碰（预留边缘）、市场规则变更需复核、市场熔断告知；不可关闭（L3，安全类）——停电、电池告警、安全相关。

**静默时段校验规则（九条）**

1. **系统强制区间** `[23:00, 07:00)`，按站点本地时区，永久生效，用户与安装商都不能关闭或缩短。
2. **有效静默区间 = 系统强制区间 ∪ 用户自定义区间**；用户自定义只能**向外扩展**（例：22:00–08:00，或 13:00–15:00 午休）。
3. **跨度限制**：自定义区间单次跨度不超过 16 小时，且不得与系统强制区间构成 20 小时以上连续静默；超出则保存失败并提示「静默这么长，紧急情况也通知不到你了。」
4. **推送时间窗校验**：必须完全落在有效静默区间之外；冲突时保存失败并给顺延建议（「我帮你顺延到 07:30」）。
5. **频率上限**：超限的非紧急通知降级为 App 内消息（不推送），并在下一次日报中合并说明；上限只允许调低，不允许调高。
6. **静默抑制的是推送通道，不是可见性**：静默期内的 L2 请示与任何降级，在 App 内消息与全局模式条上**即时可见**（§5.3 硬规则 1：任何降级不得静默发生），只是不产生推送；静默结束后 30 分钟内合并送达一条「夜里发生过 1 件需要你知道的事」。
7. **L3 例外**：停电、电池告警、安全相关事件不受静默时段与频率上限约束，立即多通道通知并记录 `Notification.suppressed = false`。
8. **时区**：一律按站点本地时区计算；用户出差改手机时区不影响系统强制区间。
9. **安装商侧不可覆盖**：安装商与沃太运营都无权为客户关闭安全类通知。

| 校验失败场景 | 文案 |
|---|---|
| 静默与推送时间窗冲突 | 「这个时间你希望安静，可你又想在这个点收到计划。我把计划顺延到 07:30，行吗？」 |
| 静默跨度过长 | 「静默这么长，紧急情况也通知不到你了。要不要缩短一点？」 |
| 上限调高 | 「每天最多 3 条是我的上限。通知太多，我自己也会变成噪音。」 |

## 7.3 自动化

| 字段 | 控件 | 说明 |
|---|---|---|

# 第八章 客诉话术 SOP 的界面化

> §10.3 第 2 条要求「『为什么半夜充电』必须有标准解释路径」。本章把它做成可复用的**界面模块**，而不是一段客服培训材料。

## 8.1 模块定位与复用点

模块名称：**「为什么这么做」解释模块**。它把一条决策（或一段异常）变成三步固定结构的说明卡，所有需要解释的地方都直接挂载它，不另写文案。

复用点与挂载形式：今日 → 执行时间线，点击任一时段的侧边抽屉内；决策日志 → 单条详情，作为详情页主体（取代原 L2 展开区，L3 深挖仍保留在下方）；影子期对照表 → 行内展开；安装商 → 生成客户沟通话术的生成器骨架（可编辑后导出）；客服 / 售后 → 工单回复草稿（自动填充，发送前过合规检查）；季度复核 → 收益复盘，引用同一模块解释某一类动作。

## 8.2 三步内容结构（顺序不可换）

**第一步 · 先给当日电价曲线**（把「半夜」翻译成「电最便宜的时段」）

- 呈现：24 小时电价曲线（单色 + 一个强调色），高亮本次动作窗口，标注「昨天全天最便宜的 2 小时」。
- 文案：「昨天 {动作窗口} 在充电。这两个小时是昨天全天电价最低的时段——比傍晚便宜约 {x} 分钱。」
- 先回答"时段选择"再谈钱：先给钱会显得生硬。
- 数据缺失时：曲线置灰 +「当时的电价数据我没取到，所以这张图不显示。下面的数字仍然是真的。」**不得编造曲线，不得用最后已知值冒充。**

**第二步 · 再给收益对照**（花了多少 / 避免了多少 / 最后净多少）

- 三行数字 + 一条净额结论：①「这个时段充电花了：€0.42」；②「如果不在这里充、改到傍晚充：€1.60」；③「扣掉存取的损耗和电池折旧：€0.18」。
- 结论句：「所以这一晚净省约 €0.61（预计 €0.48–0.72）。」
- 必须遵守：净额口径（含往返效率损失与电池循环折旧）、区间表述、不单独宣传毛价差；点击任一数字可展开构成。
- 不确定时：「电价数据今天的可信度不高，我按保守方式做的判断，这个数字可能偏高。」

**第三步 · 最后给出"你也可以改成备电优先"的选项**（把控制权交回去）

- 三个出口，横向排列，至少一个可点：`[保持这样]`（仅关闭本卡，不写规则）；`[晚上尽量别充]`（触发分流提问「这次是例外，还是以后都这样？」——「就这一次」记为一次性例外，「以后都这样」进入规则变更流程）；`[改成备电优先]`（进入红线变更 L3 申请，展示收益与风险影响）。
- 固定收尾句：「如果你希望安静一点的时段不充电，我按你说的做。」
- 禁止：不得争辩、不得反复劝说、不得表达不满（§6.6 第 12 条）。

## 8.3 数据输入契约

| 变量 | 来源 | 缺失时的降级 |
|---|---|---|
| `decisionId` / `slotWindow` | `DecisionLog` / `PlanSlot` | 缺失则本卡不可用（不应发生） |
| `priceCurve[]` + `priceSource.updatedAt` | `PricePoint` | 第一步置灰并声明 |
| `chosenWindowPrice` / `alternativeWindowPrice` | `PricePoint` | 第二步只给绝对值，不给对比 |
| `grossSaving` / `efficiencyLoss` / `depreciation` / `netSaving{min,likely,max}` | `AttributionItem` | 缺失则第二步说明「我算不清这次到底省了多少」并给原因 |
| `forgone[]` | `ForgoneOpportunity` | 为空时补一句「那天没有放弃什么机会」 |
| `guardrailTouched` | `Guardrail` | 命中备电或预算时，第二步下方必须加一行说明 |
| `marketPackVersion` | `MarketPack` | 用于口径追溯 |

## 8.4 状态与禁止事项

状态：加载中（骨架屏保留三步结构与行高）；部分缺失（哪一步缺就置灰哪一步，其余仍显示）；不可用（决策已撤销或被人工接管时改用事故简报入口）；权限不足（非家庭决策人查看时给只读版，隐藏第三步出口，改为「让家里的决策人来改」）。

四条禁止：不得只有第一、二步而没有第三步（这是"解释"退化成"辩解"的分界线）；不得只给结论不给依据；不得出现「保证 / 确保省」类表述；不得用「你不用担心」这类否定用户感受的说法。安装商 / 客服侧差异：对外发送前必须过话术合规检查；客服版可附内部根因标签，但标签不得随对外文本导出。

# 附录 B · 与总 PRD 的差异、假设与待确认事项

**B1 与总 PRD 一致、无需复核**：六条硬约束、三问的三项内容、影子期天数区间（14–28 天，默认 14）、模式迁移规则、熔断进入保守模式、安装商不能改红线、通知静默区间、七市场推进节奏。

**B2 本拆解主动做出的补充决定（建议评审确认）**

| # | 决定 | 理由 |
|---|---|---|
| 1 | 滑杆初值 40/40/20，但「以后再说」时生效值为 30/50/20 | 前者遵循 §4.9，后者遵循 §2.5「默认值必须保守」；两者混用会产生歧义，故显式分开并写入说明 |
| 2 | < 1024 断点允许纵向滚动 | 「单屏完成」的实质是**不加分页、不逐步跳转**，小屏强行不滚动会牺牲可读性 |
| 3 | 影子期默认 14 天，可延至 28 天，每次 +7 | 总 PRD 只给区间，未定步长 |
| 4 | 熔断需双人确认（发起 + 批准） | §5.4 只要求"能停"，未定权限；此动作影响多户，按 §6.5 精神加审批门 |
| 5 | 熔断后进入保守模式而**不是**回退出厂策略 | §5.4 写的是 Conservative；本拆解补上区分文案，避免误解 |
| 6 | 安装商侧一键回退需客户授权码 | §4.11 把它列为安装商工具，但用户侧同功能无需授权；补授权码以免安装商替客户做决定 |
| 7 | 备电换算的具体系数（0.35 kW、92%、10% / 90% 上下限） | 总 PRD 未给数值，本文给可实现参数，需按实测标定 |
| 8 | 通知频率上限取 3 条 / 日、10 条 / 周 | 总 PRD 只写"频率上限"，未给数值 |

**B3 待核实事项（与总 PRD 附录 B 一致，本文不解决）**：七市场的电价机制、电网费构成、上网费率与限制、居民容量费 / 需量费现状（策略运营逐市场核实后写入 `MarketPack`）；电池可用容量、放电效率、循环寿命与折旧成本（按电芯参数与质保条款标定）；家庭基础设备与追加设备功率（按目标市场实测分布标定）；"质保必需数据"的删除边界（法务出具正式意见）；安装商角色权限矩阵（与渠道赋能、法务共同确认）。

**B4 需产品负责人裁决的一个开放问题**：对"数据不全天数 > 3 天"的用户，影子期小结是否应提供"延长影子期"的强建议（默认勾选）。本文目前处理为**只提示、不默认勾选**，理由是避免把系统自身的数据问题转嫁给用户的时间成本。
