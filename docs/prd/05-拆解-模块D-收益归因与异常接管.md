## 1. 模块边界

### 1.1 职责与不做的事

| 页面 | 回答的问题 | 定位 |
|---|---|---|
| ⑥ 收益 | 这一段时间，钱省在哪了 | 把 Agent 的价值变成可验证、可对账、可回溯的数字 |
| ⑦ 异常 | 出事的时候，人和机器怎么交接 | 把每一次兜底变成有标准交接物、有闭环结论的事件 |

**必须做到**：任一数字可点进去看到构成与来源（原则 P6）；对外只有一套净额口径（总 PRD §6.2）；每个异常都产出六要素简报；每次处置都回写"这一次 / 这一类"。

**明确不做**：不产生或修改任何调度动作（本模块只读，唯一写动作是"降级 / 切安全模式"的状态请求）；不修改护栏与红线（属 L3，只能发起申请）；不替用户签合同、不承诺收益、不做零售商比价；不直接对投诉给出最终答复；不接入真实账单结算；人工接管期间不执行任何优化或降级判定（总 PRD §5.3 硬规则 2）。

**冲突裁决**：安全优先于经济（负收益若因切安全模式，报告必须把安全事件作为首要解释）；实测优先于估算（"管家"栏一律用实测，估算只用于基线重演）；口径不完整时宁可不给结论。

## 2. F6 四栏对照表的字段级规格

收益页自上而下固定五段：**① 结论条 → ② 四栏对照表 → ③ 收益拆解（8 项）→ ④ 趋势与周期切换 → ⑤ 合同体检 + 口径说明（默认折叠）**。任一段降级时不得整段消失，只允许替换为同等占位的降级说明卡。

### 2.1 四栏定义与计算口径

| 栏 | 字段名 | 定义 | 口径 | 数据来源 | 方式 |
|---|---|---|---|---|---|
| 什么都不做（没有光伏和电池） | `baselineDoNothing` | 若从未装光伏和电池，同样用电、同样电价要付多少 | 本期实际负荷 + 本期实际电价与网费，按"全从电网买"重算 | F1 `LoadSeries` + F8 `PricePoint` / `GridFeeRule` | 反事实重演 |
| 出厂默认策略 | `baselineFactory` | 装了系统但用出厂写死的"自发自用优先"，不问电价 | 同一负荷、同一实际光伏出力、同一电价，按出厂策略重跑调度 | F2 光伏实际出力 + 策略包出厂定义 | 反事实重演 |
| **管家 Agent 调度** | `agentActual` | 实际发生了什么 | 本期实际购电 × 实际电价 + 实际网费 + 实际税费 − 实际上网收益 | 电表 / `EnergyFlow` + 账单对账输入 | **实测优先** |
| 理论最优（事后回看） | `theoreticalOptimal` | 若每步都踩在最值钱的时段（事后才知）能到哪 | 真实电价、光伏、负荷；受功率/容量/效率/备电预留约束；**不受**循环预算与收益门槛约束 | 同期全量数据事后求解 | 事后求解 |

**必须写进口径说明的两条定义**：理论最优不心疼电池，它代表"不考虑寿命的数学上限"，不是追求目标；理论最优不允许为冲上限把备电压到用户目标值以下。

### 2.2 字段级展示规格

| 字段 | 位置 | 呈现规则 | 边界情况 |
|---|---|---|---|
| `label` | 第 1 列 | 固定文案；"管家调度"加粗 + 强调色左标 | 影子期改为"管家建议（未执行）" |
| `costEur` | 第 2 列 | 月度取整到 €1，日粒度 €0.01；单位只在表头出现一次 | `null` 显示"—"并给出原因短句 |
| `deltaVsBaseline` | 第 3 列 | 累进差额，节省为正；正数带"省"字前缀 | 为 0 显示"持平"；绝对值 < €1 显示"<€1" |
| `deltaVsPrevRow` | 第 4 列 | 相邻差额（第 2→3 栏即"本产品创造的价值"） | 该栏为负时改用"多花"表述 |
| `note` | 第 5 列 | 一句话说明，≤ 24 字 | 无内容时显示该栏的降级说明 |
| `basisKind` | 悬停 | `重演` / `实测` / `事后求解` | 缺值即视为数据异常，阻断渲染 |
| `sourceRefs` | 点击展开 | 来源清单 + 各自时间戳（满足 P6） | 任一来源过期 > 48 小时标灰 |
| `incompleteDays` | 页脚 | 口径不完整天数 | > 0 时页脚提示"本期有 N 天数据不完整" |
| `caliberVersion` | 页脚 | 口径版本 + 生成时间 | 与上期不同时顶部提示"本月口径有变更" |

**与数据模型文档的字段对应**：本表即 `E41 EarningsCompareRow`（`label` / `billEur` / `deltaEur` / `deltaLabel` / `note` / `emphasis`），其中 `costEur` = `billEur`、`deltaVsPrevRow` = `deltaEur`、`note` = `note`，`emphasis` 恰好一行为真且必须是"管家调度"行。本文额外要求一个**与基准的累进差额**列（`deltaVsBaseline`），用于同时给出"累进"与"相邻"两种差额：总 PRD §4.6 的表头是累进口径，而"管家调度再省 €13"是相邻口径，两者都必须在界面上说得清。

### 2.3 差额列的三种命名（禁止混用）

| 界面文案 | 计算 | 表征 | 是否可作对外口径 |
|---|---|---|---|
| 这套系统带来的节省 | 第 1 栏 − 第 2 栏 | 硬件本身的价值 | 可以，须带假设条件 |
| **管家调度多省出来的** | 第 2 栏 − 第 3 栏 | 本产品创造的价值（北极星口径组成部分） | 可以，须带假设条件 |
| **离事后最好还差多少** | 第 3 栏 − 第 4 栏 | 诚实披露的上限差距 | 可以，且**必须**披露 |

### 2.4 边界情况与降级展示

| 情形 | 判定条件 | 降级后的展示 | 文案模板 |
|---|---|---|---|
| 安装 < 14 天 | 累计有效天数 < 14 | 只留两栏（出厂策略 / 管家），标题改"暂时只做两栏对比" | "我还在学你家的用电。样本够 14 天后，我再给出完整对照。" |
| 安装 14–29 天 | 14 ≤ 有效天数 < 30 | 三栏，"理论最优"显示"—" | "事后最好的那条线，需要满 30 天数据才敢给。" |
| 影子期内 | `mode = shadow` | 第 3 栏标"如果按我说的做（未执行）"，数字必须带区间 | "这些都还没执行，是如果按我说的做会怎样。" |
| 电价缺失 ≤ 5 天 | 缺失天数 1–5 | 网费规避项不计入，差额列加星号 | "本月有 N 天电价数据不全，这部分对照仅供参考。" |
| 电价缺失 > 5 天 | 缺失天数 > 5 | 隐藏第 1、3 栏，只保留第 2 栏 + 一句说明 | "电价数据缺得太多，这个月我不给对照数字。" |
| 电表实测缺失 | 实测覆盖率 < 90% | 第 3 栏降级为算法估算，`basisKind` 标"估算" | "管家这一栏是算出来的，不是量出来的。" |
| 月中回退出厂策略 | 回退日期在报告期内 | 按回退日拆成两段，各自独立给差额 | "你在 X 日换回了出厂策略，这个月的账分成两段算。" |
| 家庭结构变化 | 基线负荷月内位移 > 20% | 第 1 栏拆前后两段重演 + 页脚注 | "你这个月用电明显变了，前后两段不可直接相加。" |

| 市场异常 / 熔断 | `MarketPack.health = fused` | 表顶部插说明卡 | "这个市场的调度规则本月做过修正，数据已重新核算。" |

### 2.6 数字呈现硬规则

1. 单位只在表头出现一次；月度取整到 €1，日金额两位小数，百分比一位。
2. **舍入方向统一（宁少报不多报）**：节省类向下取整、成本类向上取整，并写进口径说明。
3. 预测值一律给区间（"预计 €1.40–2.20"），禁止单点假精度（原则 P4）。
4. 禁用词：最高可省 / 保证 / 稳赚 / 确保，全文检索作为验收项。
5. 每个数字可点开 `sourceRefs`，满足原则 P6。

## 3. 收益归因拆解规格（8 个条目）

### 3.1 结构定义

| 段 | 结构 | 回答 | 对账硬规则 |
|---|---|---|---|
| 主拆解（8 项） | `EarningsReport.attribution`（`E24 AttributionItem[]`：`label` / `amountEur` / `sign` / `note`） | 家庭视角：本期净收益由什么构成 | Σ8 项必须**精确等于**"什么都不做 − 管家"差额，不接受"其他"兜底项 |
| 增量桥（5 项） | `EarningsReport.incrementBridge`（本文对 `E23` 的扩展字段） | 产品视角：比出厂策略多省的这部分怎么来的 | Σ5 项必须**精确等于**"出厂 − 管家"差额 |

两条对账规则必须实现为**前端断言**：不等则拒绝渲染，降级为"口径校准中"（见第 4 章）。同时满足 `E23` 的两条既有约束：`netEur` = `compare[0].billEur − compare[2].billEur`（±€0.005）且等于 8 项之和；`grossEur` 等于**正项（第 1–4 条）之和**，且 `grossEur ≥ netEur` 恒成立。

### 3.2 归因互斥规则

按**电量来源分层、逐层扣除**，每一度电只归一个条目：① 光伏直接供负载与经电池供负载 → 光伏自用节省；② 从电网买入供负载的电量，按充电时段是否低于替代零售价 → 低价充电节省；③ 专为价差买入并在高价时段放出 → 高价放电节省；④ 因动作少付或多付的输配电费与容量费 → 电网费规避；⑤ 三项物理损失与税费按实际发生额扣除，不参与二次分摊；⑥ 残差必须 ≤ 总额的 0.5%，超出即判口径异常，报告不允许发布。

### 3.3 八个条目的字段级规格

| # | 条目 | 符号 | 计算输入 | 数据来源 | 边界与例外 |
|---|---|---|---|---|---|
| 1 | 光伏自用节省 | 正 | 自用光伏电量 ×（替代零售价 − 上网电价） | 光伏出力、`LoadSeries`、`PricePoint` | 无出力日为 0；上网电价 ≥ 零售价时标注"上网比自用划算" |
| 2 | 低价充电节省 | 正 | 电网充电并自用电量 ×（负荷时段零售价 − 充电时段零售价含网费） | `PlanSlot.action = grid-charge`、`PricePoint`、`GridFeeRule` | 结果为负时**原位翻转为负项样式**并保留在正项组内，加"实际是亏的"角标 |
| 3 | 高价放电节省 | 正 | 为价差放出的电量 ×（放电时段零售价 − 该电量入池成本） | `PlanSlot.action = discharge`、入池成本台账 | 负电价时段可能为负，处理同上 |
| 4 | 电网费规避 | 正 | 避免的容量费 / 需量费 + 输配电费档位差 + 可控负荷减免 | `GridFeeRule`、`MarketPack` | 当地无第二信号机制时为 0，须说明"你们当地电网费不做分时" |

## 4. 三条诚实原则的强制落地

原则来自总 PRD §4.6，不可妥协。落地方式不是文案，而是**控件与断言**：做不到就不许出报告。

| 原则 | 强制机制（控件 / 断言） | 不可绕过的约束 | 文案模板 | 验收 |
|---|---|---|---|---|
| ① 必须计入效率损失与折旧 | 拆解区默认展开；负项组无折叠控件；导出模板校验 7 条齐全 | 负项数据缺失时禁止静默省略：整表切"不含折旧口径"，顶部出现琥珀条说明口径不完整 | "存进去 100 度，取出来大概 90 度。这 10 度是我必须算给你看的成本，不算进去就是骗你。" | 删除折旧输入后应出现口径不完整横幅，而非少一行 |
| ② 必须披露与理论最优的差距 | 第 4 行固定可见、不可折叠、不可排序隐藏；差距扩大时自动插说明条 | 第 4 行渲染失败则整个四栏表拒绝渲染，不允许三栏冒充四栏 | <10%："和事后最好的那条线比，差得不多。"／10–25%："还差 €7，主要差在我不舍得让电池多跑。"／>25%："这个月离上限差得有点多，原因我列在下面。" | 尝试隐藏第 4 行时不应存在任何可用控件 |
| ③ 宁少报不多报 | 舍入方向统一；预测一律带区间；对账偏差 > 3% 时顶部进"口径校准中"，净收益改区间呈现 | 禁用词硬拦截（保证 / 确保 / 最高可省 / 稳赚 / 一定）；影子期数字必须带"如果按我说的做"前缀 | "我这个月和你的账单差了 4.1%，说明口径还没校准好。在你对账之前，我只给区间，不给单个数。" | 全文检索 + 舍入方向抽样核对 |

**发布前联合校验（全部通过才允许渲染）**：7 条非空（或已显式降级）；第 4 行有值或显式"—"；Σ7 项与四栏差额一致；全文无禁用词；预测值均带区间；口径说明段落非空。

### 5.3 异常月份（收益转负）的呈现

**排查清单六项（逐项标"是 / 不是 / 不确定"，不允许写成笼统的外部理由）**：电价结构变化（价差变小或颠倒）／天气异常（光伏显著偏少）／设备或通信问题导致的降级天数／用户操作（锁单、回退、临时突破）／家庭用电变化／口径变更（新网费或税率进入）。

**正例文案**

> 这个月净收益 −€4.2，是上线以来第一个负月份。
> 我核对了六项：电价结构变化是主因（价差从 €0.19 掉到 €0.07），有 4 天因为电价数据源失效切成了保守模式，你家用电比上月多了 11%。
> 我没有做的事：没有为了补收益去多跑电池循环。
> 你可以：把"多小的便宜值得动手"调低一档，或者这个月先这样，下个月再看。

**反例（禁止）**："受市场行情影响，本月收益为负。"（无数据、无排查、无责任）／"下个月会好起来的。"（收益暗示）／"建议您更换电价合同。"（越界推荐）

## 6. 合同体检

### 6.1 定位与边界

回答"你现在这份电价合同，还适合你家的用法吗"。**不是比价工具**：不出现任何零售商品牌、产品名、报价数字；不出现"推荐更换""建议选择"；不给"能省多少"的承诺；涉及具体行动的结论属 L3，必须经人工复核后才能出现在用户界面。

### 6.2 触发条件

| 编号 | 条件 | 方式 | 优先级 |
|---|---|---|---|
| C1 | 月度报告生成时例行执行 | 系统自动 | 常规 |
| C2 | 当前电价合同剩余期限 ≤ 90 天 | 事件驱动 | 高 |
| C3 | 市场策略包版本变更且影响电价或电网费机制 | 事件驱动 | 高 |
| C4 | 连续 2 个月"管家比出厂策略多省的"低于当地门槛（默认 €5/月） | 随 L1 事件 | 中 |
| C5 | 上网收益占净收益 > 30%，或上网电价相对零售价方向反转 | 系统自动 | 中 |
| C6 | 同类家庭结构差异 > 一个档位（同市场同容量同电价产品） | 系统自动 | 低（仅内部，不对用户展示） |
| C7 | 用户主动发起（收益页"体检一下我的合同"入口） | 用户触发 | 随用户 |
| C8 | 季度复核 T5 第 4 问进入 | 流程触发 | 常规 |

### 6.3 结论模板与受控词表

结论只能取四值之一，禁止自造第五种：

| 档位 | 使用条件 | 一句话结论 |
|---|---|---|
| 适配良好 | 净收益结构健康，无 C2–C5 命中 | "你现在的合同，和你家的用法是配得上的。" |
| 基本适配 | 命中 C5 或价差结构轻微恶化 | "大体合适，不过有两处我在盯着。" |
| 建议关注 | 命中 C2、C3，或 C4 连续两月 | "有件事值得你留意，我把依据放在下面了。" |
| 信息不足，无法判断 | 数据完整度 < 80%，或策略包信息不全 | "我这个月的信息不够，不给你下结论。" |

**结论字段（`E23.contractCheck`）**：`verdict`（四档枚举，必填）；`verdictSentence`（≤ 30 字）；`signals`（三条信号：当前适配度 / 主要风险点 / 建议关注项，每条 ≤ 40 字，不得含推荐动词）；`evidenceSummary`；`disclaimer`（缺失则禁止渲染）；`reviewedBy`（仅"建议关注"档必需，无复核人时该档自动降级为"信息不足"）；`generatedAt`。

### 6.4 依据摘要必含项

数据期间与样本天数；电价曲线来源与最后更新时间；市场策略包版本；价差结构变化（本月 vs 上月日均价差）；家庭用电变化与晚高峰占比；上网量与上网占比；数据缺失说明；本期循环占用折算金额。

> 对照基线为"什么都不做"与"出厂默认策略"，两者均为事后重演结果，不是实际发生过的账单。
> "理论最优"为事后回看的上限，不受电池循环预算与收益门槛约束，不代表应当追求的目标。
> 完整假设条件清单共 16 项，随本报告一同呈现。
> 收益数字与你的实际账单可能因账单周期、税率调整、数据缺失而存在差异；对账偏差超过 3% 时，App 会以区间而非单点呈现结论。

### 7.4 口径变更留痕

| 变更类型 | 处理 |
|---|---|
| 效率参数、折旧单价调整 | 记入口径版本并在报告顶部提示；历史报告**不重算**，保留当时口径与结果 |
| 新增归因条目或改变互斥规则 | 需护栏复核人批准；变更前后不可直接环比，趋势图打分段标记 |
| 市场规则变化（网费、税率、上网规则） | 由 F8 策略包版本触发，报告标注生效日期 |

## 8. F7 分级处置规格

### 8.1 分级总览

| 级别 | 定义 | Agent 动作 | 通知对象与通道 | 时限 | 模式影响 |
|---|---|---|---|---|---|
| **L0 静默** | 小偏差与瞬时抖动，无需人知道 | 静默修正，记日志 | 无（安装商后台可查） | 当日入日志 | 不变 |
| **L1 告知** | 值得知道但不需立刻决定 | 继续运行，记入日报 / 周报 | 用户（日报 / 周报内，**不推送**）+ 安装商后台可见 | **24 小时内**入报 | 不变 |
| **L2 请示** | 需要用户点头，或需要降级保命 | **降级为 Conservative**，等待确认 | 用户（推送）+ 安装商（后台可见） | **同步**（60 秒内推送） | Auto → Conservative |
| **L3 紧急** | 安全相关，必须立刻叫人 | **立即切 Safe，停止一切优化** | 用户 + 安装商 + 沃太售后 | **立即**（60 秒内多通道） | 任意 → Safe |

### 8.2 L0 判定条件

| 编号 | 判定条件 | Agent 动作 |
|---|---|---|
| L0-1 | 计划时段实际执行与计划的电量偏差 < 0.4 度，且功率偏差 < 10%，持续 < 30 分钟 | 修正记录 + 日志，不改计划其余部分 |
| L0-2 | 15 分钟粒度电价点缺 1 个且可线性插值补全 | 插值补全并标注数据修补 |
| L0-3 | 当日光伏预报与实际偏差 < 15%，且发生在白天时段 | 记录，不修正已过时段 |
| L0-4 | 电池温度在正常区间内波动 < 3 摄氏度，单体温差仍在安全阈值内 | 记录，进入健康趋势 |
| L0-5 | 单次动作的收益偏差绝对值 < €0.20 | 记录到该动作的事后结果 |
| L0-6 | 日内静默修正幅度 < 当日计划的 10%，且修正后仍高于备电预留目标 | 静默修正 + 记 `PlanRevision`（标记为静默） |

### 8.3 L1 判定条件

| 编号 | 判定条件 | Agent 动作 | 附加要求 |
|---|---|---|---|
| L1-1 | 单日净收益低于当日计划区间下限，偏差 > 25% | 继续运行，记入次日日报 | 日报中给出偏差原因 |
| L1-2 | 连续 3 日净收益低于出厂策略，日均差 > €0.50 | 记入周报 + 三日明细 | 计入合同体检 C4 计数 |
| L1-3 | 月度结算净收益为负 | 记入月报 + 自动生成异常页事件 | 必须附六项排查清单（见 5.3） |
| L1-4 | 月度循环预算消耗 ≥ 50% 且距月末 ≥ 7 天 | 电池页顶部提示条 + 月报说明 | 文案不制造焦虑（"月底前我会收紧"） |
| L1-5 | 家庭画像结构性漂移：基线负荷位移 > 20% 且持续 ≥ 5 天 | 更新画像并记入周报 | 区分"事实"与"猜测"后再告知 |
| L1-6 | 月度与账单对账偏差 > 3% | 报告顶部进"口径校准中" | 净收益改为区间呈现 |
| L1-7 | 电价合同剩余 ≤ 90 天，或市场策略包版本变更 | 更新合同体检结论 | 结论受限，不得给推荐 |
| L1-8 | 电池单体温差 > 8 摄氏度，且尚未达到 L3 告警阈值 | 记入周报 + 提高温度保护强度档位 | 与数据模型文档的 L1 判定口径一致；不得写成"电池有问题" |

### 8.4 L2 判定条件

| 编号 | 判定条件 | Agent 动作 | 通知与时限 |
|---|---|---|---|
| L2-1 | 任一时刻计划将把备电可用时长压到用户目标值的 **100%–90%**（进入边缘带） | 立即切 Conservative，不执行该动作 | 推送用户 + 安装商后台可见，60 秒内 |
| L2-2 | 本次动作将导致月度循环预算 **> 100% 且 ≤ 115%** | 挂起动作，给"这次破例 / 这月就这样"两个选项 | 同上，并说明对寿命的影响 |
| L2-3 | 电价数据源失效 > 30 分钟，或数据新鲜度超期 > 45 分钟 | 切 Conservative（只做自发自用 + 备电优先） | 同上，恢复后必须汇报 |
| L2-4 | 光伏预报置信度 < 0.5 且当日存在套利动作 | 放弃该套利动作，转 Conservative，说明"这个时段的判断不可靠" | 同步 |
| L2-5 | 首次启用某类新策略、新电价产品，或参与一次需求响应奖励 | 挂起，出确认页（L2 事前确认，总 PRD §4.8） | 推送用户，未确认则不启用 |
| L2-6 | 用户提出一个 Agent 判断不划算但未越安全红线的要求 | 先执行用户意愿，再解释风险与代价 | 立即响应，事后告知 |
| L2-7 | 计划被安全原因覆盖，且覆盖幅度 > 当日计划的 30% | 切 Conservative，告知覆盖原因 | 推送 + "我改了这个计划，因为……" |

**L2 行为约束**：用户不响应时保持 Conservative，不自动回 Auto；24 小时后只再提醒一次，之后并入日报，不得反复弹窗；L2 出现频率若持续 > 1 次/天，视为产品失败信号（总 PRD §4.8 检验标准）并进入内部质量看板；L2 不接受"以后都这样"来豁免备电红线，红线变更仍走 L3。

### 8.5 L3 判定条件

| 编号 | 判定条件 | Agent 动作 | 通知与时限 |
|---|---|---|---|
| L3-1 | 并网点失电（停电）持续 ≥ 30 秒 | 立即切 Safe，停止一切优化，保住备电供关键负载 | 用户 + 安装商 + 售后，60 秒内多通道 |
| L3-2 | 电池告警：温度超阈值、单体温差超阈值，或 BMS 报警位有效 | 立即切 Safe，禁止充放电 | 同上 |
| L3-3 | 电量读数在 5 分钟内跳变 ≥ 15%，或与能量守恒核算不符 | 立即切 Safe，标记读数不可信 | 同上 |
| L3-4 | 收到电网限功率、防逆流或并网安全相关指令 | 立即遵从并切 Safe，记录指令原文 | 同上 |
| L3-5 | **备电失守**：停电期间实际可用时长 < 用户目标值的 80% | 切 Safe，生成高优先级简报 | 同上，且 24 小时内必须人工回访 |
| L3-6 | 设备通信中断 > 15 分钟，无法读取状态 | 切 Safe（不可盲目调度） | 同上 |
| L3-7 | 同市场同策略包版本下同类异常涉及 > 50 户 | 触发全局熔断，受影响用户统一进 Conservative | 运营 + 护栏复核人 + 全量受影响用户 |

### 8.6 升级、去重与优先级

| 规则 | 内容 |
|---|---|
| 升级 | L1 同类条件连续 3 天未改善 → 升 L2；L2 恶化到 L3 阈值 → 升 L3；L3 未闭环 > 72 小时 → 升级至售后负责人并计入工单超时 |
| 禁止降级 | 不允许自动把 L3 降为 L2；须人工确认告警解除，且只能回到 Conservative（总 PRD §5.3） |
| 去重 | 同一根因、24 小时内的多条同类事件合并为 1 条，时间线追加而不新开事件；合并次数必须显示 |
| 优先级 | 展示与通知优先级 L3 > L2 > L1 > L0；L3 期间 L0/L1 不推送，仅记录 |
| 静默期例外 | L3 不受静默时段抑制；L2 落在 23:00–07:00 时推送延后至 07:00，但 Agent **立即降级不等通知** |
| 接管冻结 | 事件置为 Manual Hold 后，Agent 停止一切优化与判定，只记录 |

## 9. 事故简报六要素规格

简报即 `E25 Incident.briefing` 的六个字段，是 F7 交给人的标准交接物：**所有人看同一套格式**（总 PRD §10.3 SOP 1）。

### 9.1 通用语气规则

| 规则 | 内容 |
|---|---|
| 语态 | 第一人称陈述（"我"=Agent）。只说做过什么、看到什么；推测必须标明是推测 |
| 情绪 | 不写空话道歉、不推责（不写"这是电网的问题"）、不承诺（不写"不会再发生"） |
| 标点 | 不用感叹号；每字段最多一个长句加必要分句 |
| 术语 | 遵循总 PRD 附录 A：说"还剩多少 / 够用几小时"，不说内部百分比与缩写 |
| 超限处理 | 超出字数上限时由系统截断并打标"内容被截断"，**不允许静默丢弃句子** |
| 完整性 | 六字段全部非空才允许发布；确实无内容时写"暂无"，不得留白 |

### 9.2 六要素字段级规格

| 字段 | 字数上限 | 语气要求 | 必须包含 | 禁止包含 |
|---|---|---|---|---|
| ① 发生了什么（`what`） | 60 字 | 事实叙述，过去式 | 开始时间（含日期或时点）、现象、是否仍在持续 | 专业缩写、原因推测、形容词堆砌 |
| ② 我的判断与依据（`why`） | 80 字 | 判断与依据分离，推测必须声明不确定 | 当时的电价或天气、设备状态、我的判断（至少两项）；推测时写明"我还不确定" | 把推测写成结论；引用用户看不到的内部数据而不给来源 |
| ③ 我做了什么（`whatIDid`） | 60 字 | 动作清单，动词开头 | 切到了哪个模式、停止了什么、保留了什么（尤其备电） | 只写"已处理""已优化"这类无信息量表述 |
| ④ 现在的状态（`currentState`） | 50 字 | 陈述 + 一个可核对的数字 | 备电还能撑多久（小时）、设备是否在线、是否仍在安全模式 | 乐观化描述；用百分比代替"够用几小时" |
| ⑤ 建议动作（`suggestion`） | 60 字 | 祈使句，最多 3 条，按优先级 | 每条以"你可以……"开头；无必要动作时明确写"你什么也不用做" | 推荐具体合同或产品；制造焦虑；超过 3 条 |
| ⑥ 需要谁决策（`whoDecides`） | 20 字 + 一句理由 | 单选枚举 + 理由 | 取 `user` / `installer` / `support` 之一，并说明"为什么是他" | 多选；写"请联系相关部门"这类无指向表述 |

**与数据模型文档的约束关系**：`E25.briefing` 规定"六项全部非空，每项 20–140 字"，本表给出的是**更严格的分字段上限**（60 / 80 / 60 / 50 / 60 / 20 字），取值必须同时满足两处：下限 20 字（`whoDecides` 的上限恰好也是 20 字，即该项只有 20 字这一档），上限取两者中更小者。

### 9.3 完整示例（L3 停电事件）

| 字段 | 内容 | 字数 |
|---|---|---|
| 发生了什么 | 今天 18:42 这个片区停电，你家的电已经切到电池供电，现在还在停电状态。 | 33 |
| 我的判断与依据 | 停电前你的电池还剩够基础用电约 11 小时的电量；天气正常，光伏已停发；我判断这是片区停电，不是你家设备故障。 | 51 |
| 我做了什么 | 我立刻停掉了所有为了省电费的充放电安排，把电全部留给冰箱、照明和网络。 | 33 |
| 现在的状态 | 电池还能撑大约 9 小时，设备在线，目前处于安全模式，不会自己恢复自动。 | 32 |
| 建议动作 | 你可以先别用大功率电器；如果停电超过 6 小时，可以联系安装商确认发电安排。 | 34 |
| 需要谁决策 | 用户。是否需要延长供电安排由你决定，我在你确认前不动。 | 27 |

### 9.4 正例 5 条（可直接作为话术模板）

| 序 | 场景 | 关键句（节选） | 好在哪 |
|---|---|---|---|
| 1 | L3 电池温度告警 | ②"电池温度在 21:10 到了 47 度，超过了我能接受的范围，我还不确定是散热问题还是传感器问题。" ③"我停掉了今晚的充电，也停掉了所有放电安排。" | 判断与不确定分开写，动作具体 |
| 2 | L2 电价数据源失效 | ②"电价数据已经 52 分钟没更新了，我不敢猜价格。" ③"我切到了保守模式：只用你屋顶发的电，不做任何价差动作。" ⑤"你什么也不用做，数据恢复后我会告诉你。" | 说明"为什么不敢"，并给出"什么都不用做" |
| 3 | L2 需要突破循环预算 | ④"我这次要多用 0.6 次电池寿命，相当于本月预算的 12%。" ⑤"你可以选这次破例，或者这月就这样。" | 把代价换算成用户能懂的量 |

| 5 | L1 收益异常（并入月报） | ①"这个月净收益是负数，是上线以来第一次。原因我列在下面六项里。" ⑤"你可以把'多小的便宜值得动手'调低一档，或者这个月先这样。" | 不制造焦虑，给出可操作选项 |

### 9.5 反例 3 条

| 序 | 反例文案 | 违反 |
|---|---|---|
| 1 | "因电网原因导致停电，系统已自动处理，请您放心。" | 推责 + 无信息量 + "请放心"越权；未给备电时长与决策人 |

## 10. 处置时间线与闭环回写

### 10.1 时间线字段（`E26 IncidentAction`）

| 字段 | 说明 | 界面呈现 |
|---|---|---|
| `id` / `incidentId` | 主键与事件归属 | 不显示 |
| `at` | 时间戳（家庭本地时区） | 左侧时间轴刻度 |
| `actor` | `agent` / `user` / `installer` / `support` | 决定节点形状与标签（见 10.2） |
| `actorLabel` | `管家` / `你` / `安装商` / `沃太售后` | 左侧标签，直接取自该字段 |
| `actorName` | 具体人名，可为空 | 悬停显示，不暴露内部工号 |
| `actionKind` | `detect` `degrade` `notify` `manual-fix` `escalate` `confirm` `recover` `close` | 节点图标语义 |
| `text` | 动作描述，15–100 字人话；节点折叠时只显示前 40 字 | 节点头部 |
| `modeChange` | `{ from, to }` 或空 | 节点下方模式标签（如"自动 → 保守"） |
| `evidenceRef` | 依据引用（电价、天气、设备状态、决策日志） | 可点击展开 |
| `userVisible` | 是否对用户可见 | 内部步骤对用户折叠为"其他步骤 N 步" |
| `notifyState` | `sent` / `suppressed` / `merged` / `none` | 与通知记录列表联动 |

排序固定为时间正序；未发生的下一步以**虚线段**呈现并写明预计时点（例："等待你确认，最迟 07:00 提醒"）。

### 10.2 四类 actor 的呈现区分（形状 + 标签 + 颜色三重编码）

| actor | 节点形状 | 左侧标签 | 底色 | 点击后展开 |
|---|---|---|---|---|
| Agent | 实心圆 | `管家` | 强调色浅底 | 依据与关联决策日志 |
| 用户 | 方形 | `你` | 中性浅底 | 你的操作与授权状态 |
| 安装商 | 菱形 | `安装商` | 中性浅底 + 1px 边框 | 远程支持动作与申请记录 |
| 沃太售后 | 三角形 | `沃太售后` | 中性深底 + 白字 | 工单号与处置记录 |

### 10.3 闭环回写："这一次 / 这一类"

事件置为 `closed` 前必须由人（用户或售后）选择分流，**Agent 不得代选**。

| 判据 | 倾向 | 系统提示（不代替人决定） |
|---|---|---|
| 30 天内在同一市场出现 ≥ 3 户同类事件 | 这一类 | "同一市场还有 2 户出现过类似情况。" |
| 同一家庭 30 天内同根因出现 ≥ 2 次 | 这一类 | "这个情况在你家已经出现过 2 次。" |
| 涉及策略包缺陷、数据源问题、算法边界 | 这一类 | "这次的原因不在你家，在规则或数据上。" |
| 单次设备抖动、用户临时操作、外部偶发 | 这一次 | "看不出来这会影响到别人。" |

**选"这一次"（个案）**：归档并置 `escalation = once`；写入该家庭的例外清单（供后续判定参考）；**不修改任何规则**；通知安装商后台该事件已闭环。

**选"这一类"（系统性）**：① 自动创建规则变更任务（根因、影响户数、建议变更、验证方法）；② 提交护栏复核人审批（影响多户的变更必须人工批准，总 PRD §6.5）；③ 影响 > 50 户时必须附灰度与回滚预案（总 PRD §5.4）；④ 发布新策略包版本 → 触发存量用户复核通知（F8 规则变更提醒）；⑤ 写 `AuditEntry` 留痕（谁、何时、改了什么、为什么、影响范围）；⑥ 在异常页显示"我已把这件事升级成规则改进，编号 …，状态 …"，让用户看到闭环不是口头承诺。

**恢复汇报（回到 Conservative 时必发）**

> 我已经恢复运行了。人工处理已经结束，我现在回到保守模式：只做自发自用、优先保备电，不会再自动做价差动作。
> 接下来我会这样做：先用 3 天观察设备是否稳定；如果正常，我会告诉你"可以回到自动"；这需要你点头，我不会自己切回去。

## 11. 通知规范落地

### 11.1 通知记录列表字段（`E33 NotificationRecord` 扩展）

基础字段（`id` / `channel` / `level` / `title` / `sentAt` / `suppressed` / `suppressedReason`）见数据模型文档，本表补充本模块落地所需的扩展字段：

| 字段 | 说明 | 列表呈现 |
|---|---|---|
| `id` / `householdId` | 主键与归属 | 不显示 |
| `createdAt` | 生成时间（计数窗口以它为准） | 时间列 |
| `sentAt` | 实际送达时间 | 与生成时间不同时行内显示"推迟发送" |
| `channel` | `push` / `email` / `in-app` | 通道列（文字，不用图标代替信息） |
| `level` | `L1` / `L2` / `L3` | 级别标签 |
| `refId` / `refType` | 关联事件或报告 | 可点击跳转异常页或收益页 |
| `title` / `bodyDigest` | 标题 + ≤ 40 字摘要 | 标题列 + 摘要行 |
| `delivered` / `readAt` | 是否送达、是否已读 | 状态列（已送达 / 已读 / 未读） |
| `suppressed` / `suppressedReason` | 是否被抑制及原因 | "已抑制"角标 + 展开原因 |
| `mergedCount` | 被合并的同类条数 | "已合并 N 条" |
| `windowCount` | 计数窗口内是第几条 | "本周第 2 条" |
| `capHit` | 是否因频率上限降级为仅站内 | "因频率上限，仅站内记录" |
| `modeAtSend` | 发送时的运行模式 | 悬停显示 |

### 11.2 静默时段抑制的呈现

1. 非紧急通知落在 23:00–07:00 → `suppressed = true`，原因"静默时段"，**推迟到 07:00 后首个小时内发送**。
2. 列表中该行显示"已抑制"角标，展开可见完整句子："原定 02:14 发送，因静默时段推迟至 07:05 送达。"
3. 推迟送达的通知**不重复计数**（一次生成只计一次）。
4. L3 不受静默时段抑制，但必须标注"紧急通知，已突破静默时段"并计入年度紧急额度。
5. 静默时段内 Agent 的**处置动作不推迟**（该降级还降级），推迟的只是通知。

### 11.3 频率上限的计数规则

1. **计数对象**：仅 `push` 计次；`in-app` 不计次；月度报告邮件计 1 次且独立于上限之外。
2. **默认上限**：非紧急推送每日 ≤ 2 次、每周 ≤ 8 次（用户可下调，不得上调超过产品上限）。该配置落在偏好实体的 `maxPushPerWeek`（3–30）区间内，并新增 `maxPushPerDay`（1–3）覆盖日粒度；两个上限任一触顶即按第 5 条降级。
3. **合并规则**：同一事件 24 小时内多条通知合并计 1 次；多通道同时发送计 1 次；被抑制后补发**不重复计次**。
4. **计数窗口**：自然日与自然周（当地时区）；以**生成时间**计，不以送达时间计。
5. **超限行为**：达上限后非紧急通知降级为 `in-app` + 并入下一次日报，列表标"因频率上限合并"，`capHit = true`。
6. **紧急通道独立**：L3 不受日 / 周上限约束，单独计入年度紧急额度；但同一 L3 事件 24 小时内不得重复推送超过 3 次。

### 11.4 一年内紧急通知次数上限的可视化

| 项 | 规格 |
|---|---|
| 额度 | 每户每自然年紧急通知上限 **12 次**（按事件计，多通道合并为 1 次） |
| 位置 | 设置页"通知"区 + 异常页顶部信息条 |
| 可视化 | **12 段刻度条**：已用段实心、剩余段空心、超限段斜纹；旁边固定文字"今年紧急通知 3 / 12 次" |
| 交互 | 点击任一已用段 → 显示该次通知的时间、事件编号与摘要，可跳转异常页 |
| 阈值提示 | 用满 9 次（75%）时刻度条转琥珀（语义告警），显示"今年紧急通知用得偏多，建议复核设备状态与备电设置" |
| 超限处理 | 用满 12 次后新的 L3 仍必须发送（安全优先），但需售后值守确认真实性，并标注"超出年度额度，已人工确认" |
| 禁止 | 不得把额度用作限制安全通知的手段；不得在营销中把额度说成"省心承诺" |
